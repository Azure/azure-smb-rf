# Contributing to Azure SMB Ready Foundations

Thank you for contributing to Azure SMB Ready Foundations. This repository
contains two infrastructure-as-code implementations, an Astro documentation
site, and a partner management console. Set up and validate only the components
your change affects; there is no root Node.js project or repository-wide
`npm install` command.

## Code of Conduct

This project follows the
[Microsoft Open Source Code of Conduct](https://opensource.microsoft.com/codeofconduct/).
By participating, you are expected to uphold it.

## Before You Start

Install Git and the tools required for the area you plan to change:

| Area | Required tools |
| --- | --- |
| Bicep foundation | Azure CLI with Bicep, Azure Developer CLI (`azd`), PowerShell 7 |
| Terraform foundation | Terraform 1.12, TFLint, `azd`, Azure CLI, PowerShell 7 or Bash |
| Documentation site | Node.js 24 and npm |
| Management Console API | .NET 10 SDK |
| Management Console web app | Node.js 20 or later and npm |
| Management Console deployment | Docker, Azure CLI, `azd`, PowerShell 7 |

Azure authentication is not required for the static Bicep, Terraform, and
documentation validation commands below. Deployments and the scenario test
runners create or delete Azure resources and require the appropriate tenant,
management-group, subscription, and Entra permissions.

## Getting Started

1. Fork `Azure/azure-smb-rf` on GitHub.
2. Clone your fork and add the upstream repository:

   ```bash
   git clone https://github.com/YOUR-USERNAME/azure-smb-rf.git
   cd azure-smb-rf
   git remote add upstream https://github.com/Azure/azure-smb-rf.git
   ```

3. Create a branch from the latest `main`:

   ```bash
   git fetch upstream
   git switch -c feat/short-description upstream/main
   ```

4. Install dependencies only for the component you are changing:

   ```bash
   # Documentation site
   npm ci --prefix site

   # Management Console web app
   npm ci --prefix management-console/web

   # Management Console API
   dotnet restore management-console/api/ManagementConsole.Api.csproj
   ```

### Package Sources

Application packages resolve exclusively through Microsoft's anonymously readable
CFS proxies:

- npm: `https://packagefeedproxy.microsoft.io/npm/`, configured in
  [site/.npmrc](site/.npmrc) and
  [management-console/web/.npmrc](management-console/web/.npmrc).
- NuGet: `https://packagefeedproxy.microsoft.io/nuget/v3/index.json`, configured in
  [NuGet.config](NuGet.config). The identical
  [API configuration](management-console/api/NuGet.config) also travels with the
  API's standalone Docker build context; keep these files in sync.

Local restores, container builds, GitHub Actions, and Dependabot use these same
sources. Dependabot's proxy blocks hosts that are not declared under `registries:`
in `dependabot.yml` (the update fails with `403 egress not allowlisted`), and the
schema requires an authentication field for each entry. The CFS feeds are therefore
declared there with `token: ${{secrets.CFS_ANONYMOUS_TOKEN}}`; Dependabot rejects
literal tokens ("Tokens should be stored as a GitHub secret"). Create the
**Dependabot** repository secret `CFS_ANONYMOUS_TOKEN` with the placeholder value
`anonymous` (Settings > Secrets and variables > Dependabot). CFS accepts and
ignores it, so it is not a credential. Keep that block in sync with the `.npmrc`
and `NuGet.config` files.
npm lockfile download URLs also use CFS. Keep package versions and
integrity hashes when changing only the registry. There are no package-source
credentials or public-registry fallbacks: restoration fails closed if CFS is
unavailable. `npm audit signatures` is not used because npm cannot verify
packages installed from the CFS proxy; `npm audit` is the supply-chain gate.

## Branches and Commits

Use a short, descriptive branch name such as:

- `feat/add-network-option`
- `fix/vpn-gateway-timeout`
- `docs/update-quick-start`
- `ci/update-terraform-validation`

Conventional Commit-style messages are preferred because they make history
easier to scan:

```text
feat(bicep): add a network option
fix(terraform): correct VPN route propagation
docs(site): update deployment prerequisites
```

Keep commits focused and do not include generated output, local environments,
credentials, state files, or secrets.

## Validation

Run the checks for every component your change touches. The Bicep, Terraform,
and site commands mirror the current GitHub Actions workflows.

### Bicep

From `infra/bicep/smb-ready-foundation`:

```bash
az bicep build --file main.bicep
az bicep build --file deploy-mg.bicep
az bicep build-params --file main.bicepparam
az bicep lint --file main.bicep
az bicep lint --file deploy-mg.bicep
```

Do not commit the ARM JSON files generated by `az bicep build`.

### Terraform

From `infra/terraform/smb-ready-foundation`:

```bash
terraform fmt -check -recursive
terraform init -backend=false -input=false
terraform validate
tflint --init
tflint --format=compact
terraform test
```

Do not commit `.terraform/`, local `*.tfvars`, plans, or state files. The
committed `terraform.tfvars.example` is the safe example configuration.

### Documentation Site

From the repository root:

```bash
npm ci --prefix site
npm audit --audit-level=low --prefix site
npm run build --prefix site
```

The build validates the Astro Starlight site and its internal links.

### Management Console

From the repository root:

```bash
dotnet restore management-console/api/ManagementConsole.Api.csproj --locked-mode
dotnet build management-console/api/ManagementConsole.Api.csproj --no-restore
npm ci --prefix management-console/web
npm audit --audit-level=low --prefix management-console/web
npm run build --prefix management-console/web
```

Pull requests also audit npm dependencies, audit all transitive NuGet
dependencies, and fail on NuGet advisory warnings.
Documentation pull requests run the documentation audit and production build
without deploying to GitHub Pages.

For local development, first provision or select an `azd` environment that
contains the required Entra and Azure resource values, then run:

```powershell
pwsh ./management-console/runlocal.ps1
```

See `management-console/README.md` for permissions, architecture, environment
variables, and deployment instructions.

### Azure Deployment Tests

The scripts in `scripts/` exercise all deployment scenarios against a real
Azure subscription:

```powershell
pwsh ./scripts/test-scenarios.ps1
pwsh ./scripts/test-scenarios-tf.ps1
```

Bash equivalents are available for both tracks. These are integration tests,
not routine local checks: they deploy and tear down billable Azure resources.
Review the script configuration and confirm the active subscription and tenant
before running them.

### Dependabot Approval and Auto-merge

[Dependabot](.github/dependabot.yml) checks both npm projects and the API weekly
using the same CFS registries, retaining per-project update groups. Updates of any
version level are eligible for automatic merging, but only after validation.

The trusted [auto-merge workflow](.github/workflows/dependabot-auto-merge.yml)
runs after application or documentation CI completes. It never checks out or
executes pull-request code with its write-enabled token. It verifies that the PR:

- was authored by `dependabot[bot]`, is open and ready for review;
- comes from this repository and targets its default branch;
- still has exactly the commit that completed validation; and
- has successful required checks (skipped or neutral checks are not sufficient).

It then approves that commit (when the organization allows Actions to approve pull
requests; otherwise this step only warns, because the required checks gate the merge)
and enables squash auto-merge with a matching-head
guard. A new commit must pass validation again. Failed checks, vulnerabilities,
merge conflicts, or unmet repository rules block merging; there is no bypass.
The existing projects have build checks but no unit-test scripts or test projects,
so this flow does not claim to run unit tests.

Repository administrators must enable **Allow auto-merge**. Optionally enable
**Allow GitHub Actions to create and approve pull requests** to get the bot
approval; it is not required while the ruleset requires no approvals. The default
branch must require pull requests and the following GitHub Actions checks:

- `Web supply-chain validation`
- `Web production build`
- `API restore, audit, and build`
- `Build documentation`

Repositories that fork this project must configure these settings separately.
Workflow automation takes effect once these workflow files are
merged into the default branch. Documentation CI runs on every pull request so
its required check is never missing for API-only or web-only dependency updates.

## Pull Requests

Before opening a pull request:

1. Rebase or merge the latest `upstream/main`.
2. Keep the change focused and explain why it is needed.
3. Run all validation relevant to the changed files.
4. Update documentation when behavior, prerequisites, parameters, or workflows
   change.
5. Include validation results and note any checks you could not run.
6. Confirm that no secrets, generated output, Azure state, or local environment
   files are included.
7. Complete the pull request template, checking only the items that apply and
   explaining any relevant checks you could not run.

Open the pull request against the `main` branch of
`Azure/azure-smb-rf`. Reviewers may request additional deployment evidence for
changes that affect Azure resources, permissions, policies, or teardown
behavior.

## Reporting Bugs and Requesting Features

Open an issue in
[Azure/azure-smb-rf](https://github.com/Azure/azure-smb-rf/issues) and include:

- a clear description and expected behavior;
- steps to reproduce or a concrete use case;
- the affected IaC track or application component;
- relevant tool versions and environment details; and
- sanitized logs or error messages when applicable.

Never include credentials, tokens, subscription secrets, tenant-private data,
or unredacted deployment output.
